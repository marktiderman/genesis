# @marktiderman/genesis-ui

Genesis's web components: elements, patterns, layouts and data-bound views on shadcn/ui and
Radix, styled only through the design system's tokens. Layer **foundation**, group **core**;
essential (every Genesis web app starts with it). The React Native counterpart is
[`genesis-ui-native`](../ui-native/README.md), with the same component names.

## Install

```bash
pnpm add @marktiderman/genesis-ui @marktiderman/genesis-design-system @marktiderman/genesis-core
```

React 19 and Tailwind CSS 4. The other peer dependencies (Radix, date-fns, recharts, Tiptap and
so on) are needed only by the components that use them.

## Entry points

| Import | What it holds |
| --- | --- |
| `@marktiderman/genesis-ui` | Every element and pattern from one place |
| `@marktiderman/genesis-ui/<component>` | One component, e.g. `/button`, `/settings-row` (smaller bundles) |
| `@marktiderman/genesis-ui/patterns` | Composed components with slots |
| `@marktiderman/genesis-ui/layout` | `AppShell`, `PageHeader`, page and detail layouts |
| `@marktiderman/genesis-ui/data` | `ResourceView`, `RecordView`, `RecordPeek`, `CustomView`, the view types, `DataPageShell`, `ResourcePage` |
| `@marktiderman/genesis-ui/hooks/*` | The hooks behind the patterns |
| `@marktiderman/genesis-ui/router/react-router`, `/router/tanstack-router` | Link and navigation adapters |
| `@marktiderman/genesis-ui/styles.css` | The component styles, and the `@source` that lets Tailwind see the package's classes. Without it, add `@source "../node_modules/@marktiderman/genesis-ui/dist";` |

## Quick start

A list screen is a view, not a hand-built table:

```tsx
import { defineView } from "@marktiderman/genesis-core/resource-view";
import { ResourceView } from "@marktiderman/genesis-ui/data";
import { contracts } from "./resources.genesis"; // written by `genesis introspect`

const tasksView = defineView(contracts["public.tasks"], {
  columns: { default: ["title", "due", "status"], compact: ["title"] },
});

export function TasksScreen() {
  return <ResourceView view={tasksView} />;
}
```

A form with no list around it (beside a sortable list that reorders in one write, say) takes the
same view, and gets the form `ResourceView` would open: its fields, links as pickers, the viewer's
scope and the view's words.

```tsx
<ResourceForm view={tasksView} action="create" open={open} onOpenChange={setOpen} filter={{ project_id }} />
```

`useViewFormFields(view, { filter, defaults })` returns those fields for a form of your own.

The same view shows as a calendar with `type="calendar"` (its `calendar` block, the screen's
overrides in `calendar={…}`): a layout switch (`layouts`), a weeks switch (`weeksOptions`), the
screen's own controls beside them (`toolbar`), and a colour per lane with `colorLanes`. All-day rows
are best stored as days; stored as UTC midnight they stay on their day on any clock.
`laneColor(i)` from `/data` gives the colour for lane `i`: the theme's chart colours, then distinct
ones past five. See [Calendar](../../docs/RESOURCE-VIEW.md#calendar).

```tsx
<ResourceView view={tasksView} type="calendar" calendar={{ layouts: ["weeks", "lanes"], weeksOptions: [1, 2, 4], colorLanes: true }} />
```

Theme it with [`genesis-design-system`](../design-system/README.md): import
`@marktiderman/genesis-design-system/themes/genesis.css` and `themes/genesis-tailwind4.css` after
Tailwind, as its README shows; a brand of your own replaces them with CSS generated by
`tailwindFromBrand`.

## View types, record pages and custom views

How a view shows is its **view type**: `<ResourceView view={…} type="board" />` (`mode` is its
alias). Genesis has `table`, `list` and `grid` (the person switches between them), `board`,
`calendar` and `gallery`; an app adds its own and every screen picks it the same way:

```tsx
import { defineViewType, registerViewType, ResourceView, useViewList, type ResourceViewProps } from "@marktiderman/genesis-ui/data";

function Timeline({ view }: ResourceViewProps) {
  const list = useViewList(view);
  return <ol>{list.rows.map((row) => <li key={list.keyOf(row)}>{String(row.title)}</li>)}</ol>;
}
registerViewType(defineViewType({ id: "timeline", render: Timeline }));

<ResourceView view={tasksView} type="timeline" />;
```

A record opens as a **record page**: a side peek, a center peek or its full page, as the view's
`open` says (`defineView(…, { open: "center-peek", recordView: (): AnyRecordView => taskRecordView })`), from the
list, the board and the calendar alike. A peek draws the view's record view when it names one
(`RecordPeek`), else its columns as before; a screen's `open`, or ResourcePage's `detail`, wins. A
record view's `template: "document"` lays the page out as a cover, an icon, a title, the
properties and the body.

A **custom view** is a screen an app draws itself over a view:
`<CustomView view={…}>{(state) => …}</CustomView>` keeps the view's data, URL, live updates and
permissions and draws loading, empty and error; the app draws the rows (its own elements are
parts named `app-…`). See [View types, record pages and custom views](../../docs/RESOURCE-VIEW.md#custom-views).

## Sign-in pages

`AuthForm` (from the root or `/patterns`) is the web sign-in form, inside `AuthPage`: sign in with
a password, a magic link or an emailed code, sign up, forgot password and the new password a reset
link opens, with provider buttons. It draws the steps and the words; every call goes through the
`client` it is given. On Supabase that is `createAuthFormClient` from
[`genesis-supabase`](../supabase/README.md#on-the-web-authform), which also finds the providers the
project has turned on.

```tsx
import { AuthForm, useUiMessages, type AuthFormClient, type AuthFormMode } from "@marktiderman/genesis-ui";
import { AuthPage } from "@marktiderman/genesis-ui/layout";

function SignInPage({ client }: { client: AuthFormClient }) {
  const [mode, setMode] = useState<AuthFormMode>("sign-in");
  const { titles } = useUiMessages().auth;
  return (
    <AuthPage branding={{ logo: <Logo />, headline: titles[mode] }}>
      <AuthForm client={client} mode={mode} onModeChange={setMode} methods={["password", "email-code"]} onSuccess={() => navigate("/")} />
    </AuthPage>
  );
}
```

- **Modes**: `"sign-in"`, `"sign-up"`, `"forgot-password"`, `"new-password"`; controlled
  (`mode`, `onModeChange`: a route per mode) or not (`defaultMode`).
- **`methods`**: how to sign in, the first shown and the rest offered as links
  (`"password"`, `"magic-link"`, `"email-code"`, `"phone-code"`).
- **`"phone-code"`** (opt-in, through `methods`): a phone number field (`type="tel"`,
  `autocomplete="tel"`) instead of the email, a code texted to it (`client.sendPhoneCode`), and
  the same code step (`client.verifyPhoneCode`). The number must carry its country code; spaces,
  dashes and brackets are dropped (`+1 (555) 123-4567` → `+15551234567`). A client without both
  calls leaves the method out (in development it says so). Without sign-up, an unknown number is
  answered as sent, as for email.
- **`signUpFields`** (opt-in): more fields on the sign-up form, whose values go to
  `client.signUp` as `data` (on Supabase, the user's metadata, which a signup trigger reads).
  `["full_name"]` adds a required "Full name" (`autocomplete="name"`); your own are
  `{ name, label, type?, autoComplete?, placeholder?, required? }`. A function is a slot:
  `({ values, setValue, disabled }) => …` draws its own inputs. Empty optional values are left out.
- **The email beside a new password**: in `mode="new-password"`, when the email is known
  (`initialEmail`, else `client.currentEmail()`, which genesis-supabase reads from the session),
  the form holds it in a hidden `autocomplete="username"` field, so a password manager saves the
  new password with its account. Nothing changes on screen; `showAccountEmail` (opt-in) shows it
  read-only instead.
- **The code step** is `InputOTP` (`autocomplete="one-time-code"`): it verifies on the last digit,
  and resends after `resendCooldown` seconds (60).
- **`codeLength` must match the project's `otp_length`** (Supabase Auth settings, "Email OTP
  length"; default 6). The code field takes exactly `codeLength` digits, so with a mismatch no
  code can be entered whole and code sign-in fails with nothing on screen to say why. Supabase's
  public `/auth/v1/settings` doesn't report `otp_length`, so the form can't check it; in
  development a refused code logs a hint to compare the two.
- **`offerCodeOnConfirm`** (opt-in): the "check your email" screens after a magic link and after
  sign-up offer "Enter the code instead", which opens the code step for the same email. For people
  in an embedded browser (an in-app web view), where the link opens in another browser. It needs
  `"email-code"` in `methods`, and `{{ .Token }}` in the Magic Link and Confirm signup templates.
- **`notice`**: a notice above the form's first step, as an `Alert`: `{ kind: "reset-link-expired" }`,
  `"provider-cancelled"` or `"account-deleted"` with the catalogue's copy (`auth.notices`), a
  `message` of your own, or a plain string. An expired link is an error (`role="alert"`), the
  others are announced politely (`role="status"`); `tone` overrides it.
- **Before hydration** a server-rendered form's submit is disabled (drawn as enabled) and the form
  is `method="post"`, so an early click or Enter neither drops what was typed nor puts the email
  in the URL.
- **Providers**: `providers={["google"]}` or objects with a label and icon; left out, it asks
  `client.providers()`; `false` for none.
- **Words** are the `auth` part of the catalogue (`UiMessagesProvider`). A failed call shows the
  copy for its error code (`auth.errors.invalid_credentials`…), else `auth.errors.generic`. The
  server's own text is never shown: for a code with no copy it goes to `reportError`. A client
  that writes a message for people marks it `displayable: true`, and that one is shown.
- **Without sign-up** (`allowSignUp={false}`), an email with no account is answered as sent
  (Supabase's `otp_disabled`), in neutral copy ("If … has an account, we sent…"), so the form
  never tells which emails have accounts.
- **`mode="new-password"`** needs the session a reset link opens: show it only after the client's
  `PASSWORD_RECOVERY` event.
- Every field is labelled and carries the autocomplete a password manager needs (`email`,
  `current-password`, `new-password`); errors are announced and tied to the field their code is
  about (`weak_password` to the password, `email_*` and `user_already_exists` to the email).
  "Check your email" takes focus when it replaces the form, and the code field stays focusable
  (read-only, `aria-busy`) while it verifies.
- Native's `AuthForm` (genesis-ui-native) is a different component: it takes `onSubmit` and
  `errorMessage`, and its `mode` is `password` or `magic-link`.

## Messaging: `ThreadPage`, `InboxPage` and `InboxLayout`

The web twins of genesis-ui-native's messaging layouts, on the shared conversation contract in
`@marktiderman/genesis-core/conversation`. The same `ThreadMessage[]` and `InboxItem[]` render on
the web and the phone, and the props and slots match, except for these.

- **Web only:**
  - `ThreadPage`: `conversationId` and `sendOn`.
  - `ThreadList`: `conversationId`, `openAt`, `announce` and `label`.
  - `InboxPage`: `selectedId`, `onSelect`, `hasMore` and `moreLabel`.
  - `InboxLayout` and `InboxViews` are web only.
- **Native only:**
  - `NativeThreadList`: `getItemType` and `jumpAnnouncement`.
  - `InboxPage`: the `swipeable` slot. The web shows a row's `swipeActions` as a "More" menu instead.
  - `ThreadPage`: `keyboardVerticalOffset`.

- **`ThreadPage`:** one conversation. It fills its container.
  - Messages oldest first in a `role="log"` region, events as centred lines, attachments and a read receipt.
  - Pass `conversationId`: when it changes (another row picked in an inbox), the thread opens afresh, at the first unread or the newest.
  - A screen reader hears someone else's new message, not each page of earlier ones.
  - While you're at the bottom it stays there as things change size: a photo loading, the typing line, the composer growing.
  - Earlier pages load near the top, with a "Load earlier" button too, and the list keeps its place while they arrive.
  - It follows the newest message only while you're at the bottom; otherwise a "Jump to latest" pill shows.
  - `firstUnreadId` adds a divider, and `jumpTo` with `onLoadUntil` goes to a message and highlights it.
  - `loading` and `updating`, and send states as data (`pending`, `paused`, `failed`, `conflict`, with `onRetry` and `onDiscard`).
  - Internal notes (`tone: "internal"`) are edged in `warning` and say so to a screen reader.
- **`ComposerBar`:** an input that grows as you type, with `modes` and a tone.
  - Enter sends; Shift+Enter adds a line. With `sendOn="mod-enter"`, Cmd/Ctrl+Enter sends instead. On a touch screen, Enter adds a line.
  - Nothing sends on the Enter that confirms an input method, in Safari too.
  - The send button stays put while sending, so focus doesn't jump.
  - Slots: `leading`, `trailing`, `above`.
- **`ThreadList`:** the list on its own.
- **`InboxPage`:** conversation rows: unread dot or count, a short time, a preview, a status line.
  - Each row's `swipeActions` become a "More" menu.
  - The rows are one tab stop that stays where you were. Arrow keys or j/k move between rows, and Right reaches a row's More menu. `selected` marks the open one.
  - A custom `row` slot spreads `rowProps` on its focusable element to keep the keyboard moves.
  - Paging (`onEndReached` asks once per page; `hasMore={false}` stops it), loading, error and empty states.
- **`InboxPage` selection:** `selectedId` and `onSelect` keep the open conversation in the app's route.
- **`InboxLayout`:** the three-pane inbox, with views (`InboxViews`: label, count, icon, active), the list, the thread and a context sidebar.
  - **Narrow screens:** one pane at a time, with Back.
  - **The context sidebar:** toggles, either controlled or remembered per browser under `contextStorageKey`. From `xl` up it sits beside the thread; below that it opens as a sheet.
  - **Keyboard (`shortcuts`):** j/k next and previous, r reply, n internal note, e close, a assign, Escape back. Each one is a callback you can leave out, and none fires while typing.

Times show once the page has hydrated, in the viewer's time zone, so server-rendered HTML has none
and hydration matches.

```tsx
import { InboxLayout, InboxPage, ThreadPage, type InboxItem, type ThreadMessage } from "@marktiderman/genesis-ui";

function Inbox({ items, messages, draft, setDraft, send, openId, open, close }: {
  items: InboxItem[];
  messages: ThreadMessage[];
  draft: string;
  setDraft: (text: string) => void;
  send: () => void;
  openId: string | null;
  open: (id: string) => void;
  close: () => void;
}) {
  return (
    <InboxLayout
      list={<InboxPage items={items} selectedId={openId} onSelect={open} />}
      thread={
        openId ? (
          <ThreadPage conversationId={openId} messages={messages} composer={{ value: draft, onChangeText: setDraft, onSend: send }} />
        ) : null
      }
      threadOpen={Boolean(openId)}
      onBack={close}
    />
  );
}
```

## App themes: component tokens, parts and the bundle

genesis-ui's components read component tokens for their sizes, shapes and
type (`--control-height`, `--card-shadow`, `--table-head-text-transform`…,
declared in genesis-design-system's `themes/genesis.css` at the values the
classes had), and every core component and the app shell mark their named
parts with `data-slot` (`button` with `data-variant` and `data-size`, `card`,
`table-head`, `shell-nav-item` with `data-active`, `shell` with
`data-density`…). An app style (`data-app-style`) sets the tokens and changes
the parts, so one stylesheet changes how every screen looks without touching a
component; an app brand (`data-app-brand`) sets the colours and typefaces on
its own. Both are genesis-design-system's
(`@marktiderman/genesis-design-system/app-styles`, ADR 0018).

An **app theme** bundles them under one name with a layout:
`defineAppTheme({ name, label, description, brand?, style?, layout? })` from
`@marktiderman/genesis-ui/themes`. Each piece is optional and one left out
keeps the app's own, so the seven starter themes (`STARTER_THEMES`, one per
starter style) come without a brand and wear the app's colours.
`appThemeAttributes(theme)` gives the attributes to set (on `<html>`, so menus
and dialogs wear it too) and `appShellOptionsFromTheme(theme)` the `AppShell`
options the layout starts from. Those are defaults: where the shell is
`configurable`, the person's own choices win (`lockedOptions` keeps
one fixed). Light and dark is the person's appearance, which no theme sets.

```tsx
import { AppShell } from "@marktiderman/genesis-ui/layout";
import { appShellOptionsFromTheme, appThemeAttributes, getStarterTheme } from "@marktiderman/genesis-ui/themes";

const theme = getStarterTheme("tracker"); // the tracker style and a compact, inset sidebar layout, in the app's brand
Object.assign(document.documentElement.dataset, { appStyle: theme?.style?.id });
appThemeAttributes(theme); // { "data-app-style": "tracker" }
const shell = <AppShell appName="Acme" navItems={[]} options={{ ...appShellOptionsFromTheme(theme), scrollRoot: "window" }} />;
```

The parts and tokens are a contract (`THEME_PARTS`, `COMPONENT_TOKENS`): a test
fails a part a component stops rendering and a token nothing reads.

## Layouts: navigation styles, frames, density and page templates

An app's **layout** is how it is navigated and framed (ADR 0022), and it is
`AppShell` options over the one navigation tree:

- `navigation`: `sidebar` (default, as always), `rail` (opens collapsed to the
  icon rail), `top-tabs` (the top items as tabs across a desktop top bar),
  `bottom-bar` (the phone's bottom bar on every width) or `page-tree` (a
  nested, collapsible tree of pages, indented by depth).
- `frame`: `flush` (default) or `inset`, the page area as a panel over the
  sidebar's colour, shaped by the `--shell-frame-*` component tokens.
- `density`: `compact`, `comfortable` (default) or `spacious`, the same words
  lists (`useViewSettings`) and sites' design systems use (`DENSITY_LEVELS`).

A theme's layout (`AppThemeLayout`: `navigation`, `frame`, `density`, rail and
sub-navigation) is the default; the app's own options and the person's stored
choices win.

```tsx
import { AppShell, DocumentPage } from "@marktiderman/genesis-ui/layout";

const shell = (
  <AppShell appName="Acme" navItems={[]} options={{ navigation: "top-tabs", frame: "inset", density: "spacious" }}>
    <DocumentPage cover="/covers/ocean.jpg" icon="🌊" title="Trip notes">
      <p>Day one.</p>
    </DocumentPage>
  </AppShell>
);
```

The page templates are `DashboardPage`, `DetailPage`, `FormPage`,
`SettingsPage` and `DocumentPage` (a cover, an icon, a title and a centred
reading column), each also on its own subpath (`/document-page`). Zones
(`NavigationNode.zone`, `resolveNavigationZones`) tell the app which area the
viewer is in, so it can set a theme per zone; the shell carries `data-zone`.

### Appearance, density and the brand in the shell

A person's appearance (light, dark or system) and density are theirs (ADR
0024). Wrap the app in genesis-core's `AppearancePreferencesProvider`, with a
store from `defineAppearancePreferences` so the choice follows them, and use
`AppearanceProvider` from `@marktiderman/genesis-ui/themes` where you used
`GenesisThemeProvider`: it shows their appearance and saves their changes.
`AppShell` then takes its density and its theme toggle from them: the app's
lock, the person, the organization's default, the theme's, then its own
`options`. `appShellBrandProps(brand)` gives `AppShell` an app brand's name and
mark.

```tsx
import { AppearancePreferencesProvider } from "@marktiderman/genesis-core";
import { AppShell } from "@marktiderman/genesis-ui/layout";
import { AppearanceProvider, appShellBrandProps } from "@marktiderman/genesis-ui/themes";

const app = (
  <AppearancePreferencesProvider preferences={appearance} organization={resolveWorkspaceAppearance(active)}>
    <AppearanceProvider brand={canonicalBrand}>
      <AppShell {...appShellBrandProps(acmeBrand)} navItems={[]}>{page}</AppShell>
    </AppearanceProvider>
  </AppearancePreferencesProvider>
);
```

## Widgets

A widget is a tile fed by a view (ADR 0023): `defineWidget` from
`@marktiderman/genesis-core/resource-view`, drawn by `<Widget>` from
`@marktiderman/genesis-ui/data`, live and in the viewer's scope, with its own
loading, error and empty states. Put them in a `DashboardPage`'s `stats` as
they are, or lay a dashboard's body out with `WidgetGrid`. `StatCard`,
`HeadlineNumbers` and `SummaryCard` draw the same tile (`WidgetTile`), so an
app style changes all of them through `widget-label`, `widget-value` and
`widget-detail`. See docs/RESOURCE-VIEW.md, "Widgets".

## Twins of the phone's components

The web side of components genesis-ui-native had first, with the native twin's props and its
behaviour from genesis-core's `@marktiderman/genesis-core/headless`:

- `Banner` and `InlineAlert` (NativeBanner, NativeInlineAlert): the Alert, tinted, with dismiss and actions.
- `ChoiceCard` (NativeChoiceCard): an option card that is a radio, or with `multiple` a checkbox.
- `ChipGroup` with `ChipGroupItem` (NativeChipGroup): the toggle Chip, single or multiple.
- `Combobox` (NativeCombobox): Command in a Popover, searched with genesis-core's `filterOptions`.
- `NumberInput` (NativeNumberInput): a spinbutton with − and + on the InputGroup.
- `RangeSlider` (NativeRangeSlider): the Slider with two thumbs (the Slider draws a thumb per value).
- `Stepper` (NativeStepper), `TimePicker` (NativeTimePicker), `WhatsNewSheet` (NativeWhatsNewSheet, a dialog that rises as a sheet on a phone-width screen) and `NotificationsPage` (the phone's NotificationsPage).

```tsx
import { useState } from "react";
import { Combobox, NumberInput, TimePicker } from "@marktiderman/genesis-ui";

export function ClassForm() {
  const [room, setRoom] = useState<string | undefined>();
  const [spots, setSpots] = useState(12);
  const [at, setAt] = useState(() => new Date());
  return (
    <>
      <Combobox aria-label="Room" options={[{ value: "a", label: "Studio A" }, { value: "b", label: "Studio B" }]} value={room} onChange={setRoom} />
      <NumberInput aria-label="Spots" value={spots} onChange={setSpots} min={1} max={40} />
      <TimePicker aria-label="Starts" value={at} onChange={setAt} minuteStep={15} />
    </>
  );
}
```
